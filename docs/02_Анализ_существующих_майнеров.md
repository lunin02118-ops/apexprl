## 2.2. Глубокий инженерный разбор ключевых Open-Source архитектур с GitHub

Прямой анализ исходного кода пяти самых продвинутых репозиториев на GitHub позволил точно установить, **почему закрытые лидеры (SRBMiner, ForgeMiner, PeakMiner) обгоняют обычные реализации на 15–28%, и как превзойти их обоих**.

### 1. Разбор `SerpentXSF/X-Miner` (`kernels/pearl/pearl.cu` и `docs/PERFORMANCE.md`)
Авторы `X-Miner` провели серию строгих лабораторных замеров с помощью **NVIDIA Nsight Compute** при фиксированной частоте ядра и при фиксированном Power Limit. Главные открытия:
* **Физика энергопотребления данных (Data-Dependent Switching Power):** на одних и тех же тактах ядро Tensor Core потребляет на реальных псевдослучайных данных Pearl **на ~45–70% больше ватт**, чем на нулевых или константных матрицах, из-за переключения транзисторных линий внутри матричных умножителей! Поэтому любые синтетические бенчмарки на нулях дают ложные частоты буста.
* **Устранение межпоточных пересылок (`Per-Lane Periodic Hash Tile`):** поскольку протокол Pearl разрешает периодические (разреженные) координаты тайла `PeriodicPattern`, выбор паттерна строк `{0, 8, 16, 24, 32, 40, 48, 56}` и столбцов `{0, 1, 8, 9, ..., 56, 57}` внутри варп-тайла $64 \times 64$ приводит к тому, что **все 128 элементов одного хеш-тайла принадлежат регистрам одного-единственного потока (`lane`) варпа**! Свёртка каждые 128 шагов $K$ превращается в чистый внутрирегистровый `lop3.b32` (3-входовой XOR) без единого `__shfl_xor_sync` или обращения к Shared Memory!
* **Проблема «дрейфа блоков по $K$» (DRAM Drift):** если запустить обычную сетку блоков по тайлам матрицы $M \times N$, блоки быстро рассинхронизируются по координате $K$, кэш L2 перестаёт попадать в общие полосы $A'$ и $B'$, и трафик видеопамяти взлетает в 2.4 раза, сжигая десятки лишних ватт. Введение 9-го продюсер-варпа (`cp.async`) с глобальным барьером старта волны подняло L2 hit rate до **81.35%**.
* **Где остался потолок `X-Miner`:** даже при 81% попаданий в L2 постоянная прокачка плотных матриц $A'$ и $B'$ из L2/DRAM в Shared Memory отнимает **~30% бюджета мощности чипа** и ~11–13% тактов на барьеры и ожидание памяти. Именно поэтому `X-Miner` останавливается на ~86–89% от пика SRBMiner.

### 2. Разбор `dartxxx/pearl-miner` (`transcript_gemm_sm120.cu` — движок Akoya Pool под RTX 50)
* Построен на шаблонах **NVIDIA CUTLASS / CuTe** (`TiledMMA<MMA_Atom<SM80_16x8x32_S32S8S8S32_TN>>`, тайл $128 \times 256 \times 128$, `Swizzle<3,4,3>` для бесконфликтного чтения `ldmatrix.x4`).
* Содержит экспериментальный путь **TMA (`SM90_TMA_LOAD`)** и кластерный запуск (`cudaLaunchAttributeClusterDimension`) для RTX 5090 (`sm_120`).
* **Почему теряет производительность (~300.8 TMAC/s на RTX 5090 в headless-режиме при потолке 419+ TMAC/s):**
  1. Прокачивает полные плотные матрицы $(M \times K)$ и $(N \times K)$ через глобальную память;
  2. В не-headless режиме сбрасывает буфер транскриптов в глобальную память и запускает отдельное ядро финализации (`launch_transcript_finalize`);
  3. Высокоуровневая абстракция CuTe генерирует субоптимальное расписание регистров в `ptxas` на архитектуре `sm_120`.

### 3. Разбор `pushsoftnow/blackwell_pearl_miner` (`bpm` — `kernels/kernel780.cu`) — ГЛАВНЫЙ ПРОРЫВ
Этот репозиторий раскрывает приём, который кардинально меняет правила игры на GPU с большими Tensor Cores:
1. **Отказ от хранения и чтения матриц $A'$ и $B'$ в глобальной памяти (`On-Chip Basis Rebuild`):**
   Вместо генерации гигабайтных матриц $A'$ и $B'$ в VRAM на GPU хранятся только компактные матрицы равномерного шума $U_A$ ($M \times 128$) и $U_B$ ($N \times 128$) весом всего по **16 МиБ** при $M=N=131\,072$!
   В начале каждого CTA-тайла $160 \times 256$ одна инструкция `cp.async.bulk` загружает в Shared Memory $20\text{ КиБ}$ базиса $A$ и $32\text{ КиБ}$ базиса $B$ (**итого 52 КиБ один раз на весь тайл!**).
   Затем на протяжении $K = 16\,384$ или $K = 65\,536$ шагов варпы собирают операнды $A'$ и $B'$ **прямо внутри Shared Memory / регистров** через `ldmatrix.sync.aligned.m16n16.x2.trans.shared.b8`! **Обращения к GDDR7 во время счёта равны НУЛЮ** (кроме 8 байт индексов пар из L1/L2 кэша на шаг $K=32$)!
2. **Беззнаковая арифметика Tensor Core (`u8.u8.s32`):**
   Прибавление константы `0x40404040u` (+64 к каждому байту) переводит разность двух шумовых компонент в беззнаковый байт `uint8_t`, позволяя исполнять `mma.sync.aligned.m16n8k32.row.col.s32.u8.u8.s32` и вычитать поправку `corr` только на единственном граничном фрагменте, если в тайл попала строка с `nonce`!
3. **Математически точная перестановка столбцов (`reorder_pairs`):**
   Поскольку внутри каждого блока из 128 столбцов $K$ операция матричного умножения — это коммутативное и ассоциативное сложение в `int32_t`, а транскрипт снимает состояние **только раз в 128 столбцов**, **порядок столбцов внутри каждого 128-столбцового окна можно переставлять произвольно без изменения результата ни на один бит!** Маленькое вспомогательное ядро `reorder_pairs` жадно группирует 128 столбцов в 16 восьмёрок так, чтобы индексы `component mod 8` попадали в разные банки Shared Memory, **уничтожая ~45% bank conflicts бесплатно!**
4. **Открытие критического бага оптимизатора `ptxas` на Blackwell (`CUDA 13.4`):**
   В файле `tuning/results/rtx-pro-4500-blackwell-cuda13.4-150w-20261113.json` зафиксирован поразительный факт: компиляция одного и того же цикла `kernel780.cu` со стандартным флагом `nvcc` **`-Xptxas -O3` или `-O2` обрушивает скорость на `-37.935%`** по сравнению с **`-Xptxas -O1`** и ручной фиксацией точек выдачи `ldmatrix`/`st.shared` (`P0..P7, PL`) внутри развёрнутого цикла `mma.sync`! Агрессивный планировщик `ptxas -O3` переупорядочивает загрузки из Shared Memory перед барьерами, вызывая лавину регистровых зависимостей и простоев Tensor-конвейера.

**Ограничения `bpm`, которые делают невозможным его прямое использование «как есть» для нашей задачи:**
* Он написан **исключительно под `sm_120`** (использует инструкции `cp.async.bulk...shared::cta` и специфичный размер Shared Memory `101 376 B`, которые **не существуют или отличаются на RTX 40-й серии `sm_89`** — на RTX 40 он просто не скомпилируется и не запустится!).
* Поддерживает только **1 видеокарту на процесс** (нет полноценного мульти-GPU оркестратора рига на 6–12 карт).
* Windows-порт помечен автором как экспериментальный и не протестированный на реальном железе (распаковка временной DLL в `%TEMP%`, нет управления частотами/энергопотреблением на Windows, нет HiveOS flight-sheet обвязки и отказоустойчивого пул-фейловера уровня `spark-pearl-miner`).

### 4. Разбор `xXGuilasXx/spark-pearl-miner` (`spm`) и `1640675651/CPPminer`
Из этих двух проектов мы забираем в нашу архитектуру лучшие системные решения:
* Из **`spark-pearl-miner`**: чистый конечный автомат пул-менеджера с мгновенным фейловером между 3+ пулами, автоматический SASS-гейт при сборке (`check-sass.py`), локальная пред-проверка 100% шар через `zk-pow::verify_plain_proof` (защита от бана на пуле при переразгоне карты!), и архитектурный шаблон под грядущий форк **FP8 (`cert_version = 4`)**.
* Из **`CPPminer`**: минималистичный `CpShareWitness` (передача с GPU на CPU только нужных строк/блоков при попадании в шару), инкрементальный Merkle-апдейт и прозрачная авто-негоциация протокола **Kryptex Gzip Stratum v2** (`miniz_oxide` / `zlib` сжатие доказательства в 35–80 раз).

### Откуда берётся суммарное превосходство собственного майнера (+5% … +12% чистой доходности на Ватт):
1. **+1.0% … +2.0% мгновенно** — полное отсутствие Dev Fee и отсутствие простоев конвейера при переключении контекста/пула на devfee-сессию.
2. **+3.0% … +7.0% по чистому хешрейту при том же лимите мощности** — перенос реконструкции матриц в Shared Memory (`Basis Kernel`) отключает контроллер памяти GDDR6X/GDDR7 от тяжёлого трафика; освободившиеся 35–75 Вт теплопакета автоматически конвертируются алгоритмом GPU Boost в **+120…+220 МГц частоты ядра Tensor Cores** (либо позволяют зажать Power Limit без потери хешрейта!).
3. **+1.0% … +2.5% за счёт микроархитектурного автотюнинга `ptxas -O1`** под конкретный SKU (`GB202` vs `GB203` vs `AD102` vs `AD103`) и подавления конфликтов банков Shared Memory (`reorder_pairs`).
4. **+0.5% … +1.0% на пуле** — субмиллисекундный сброс устаревшего задания при новом блоке (`< 0.2 мс` chunk abort) снижает долю `Stale Shares` практически до нуля.
